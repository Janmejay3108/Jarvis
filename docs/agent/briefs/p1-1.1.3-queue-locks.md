## Design Rulings

1. A queue is bound to one track. Instantiate one `TrackQueue` per configured track; each instance owns one unbounded `asyncio.Queue[AgentRun]` and one worker. There is no global worker shared across tracks.
2. Queue ordering is FIFO by successful first enqueue. A duplicate does not add another item or change the original item position.
3. Active-ticket deduplication is per track and per application process. Normalize ticket keys with `strip().upper()` and key the active map by that canonical value. The check, `AgentRun.create`, active-map insertion, `run.queued` publication, and queue insertion occur under one queue-local enqueue mutex so concurrent callers cannot create two rows.
4. Do not query old non-terminal database rows at startup and do not claim cross-process queue dedupe. Durable queue recovery needs a separate startup-reconciliation design; treating an abandoned row as live forever would make the ticket impossible to rerun. The deployed app currently has one orchestrator process. The file lock below is the cross-process safety boundary for the shared SUT.
5. Do not acquire the track/SUT lock around diagnosis. Step 1.1.3 executes the existing diagnosis pipeline, which is read-only analysis. Plan2's validation gate will acquire the lock around the authoritative validation transaction.
6. One track currently maps to one configured SUT, so the lock key is `track_id`. Do not invent suite-level locks: every suite uses the same validation branch and SUT path, and suite-level locking would permit unsafe overlap.
7. A duplicate `autofix` request must not upgrade an active `diagnose` run, and a duplicate `diagnose` request must not downgrade an active `autofix` run. Return the existing run unchanged. This preserves route conservatism.

### `src/orchestrator/locks.py`

Replace the empty placeholder with a process-local per-track lock registry backed by a native cross-process file lock.

#### Public API

```python
class TrackLockManager:
    def __init__(
        self,
        lock_root: Path = Path("data/locks"),
        *,
        timeout: float = -1,
    ) -> None: ...

    @asynccontextmanager
    async def hold(self, track_id: str) -> AsyncIterator[None]: ...
```

`timeout=-1` means wait until the protected SUT is available. Tests may supply a finite timeout. A timeout must surface as `filelock.Timeout`; do not convert lock contention into a validation FAIL.

#### Track identity and lock path

- Canonicalize `track_id` with `strip().lower()`.
- Reject an empty key or any key not matching `^[a-z0-9][a-z0-9_.-]*$` with `ValueError`. This prevents path traversal and accidental aliases.
- Create `lock_root` as needed.
- Use the stable path `<lock_root>/<canonical_track_id>.lock`.
- Cache exactly one `asyncio.Lock` and one `AsyncFileLock` per canonical track within the manager. The application dependency container must own one manager and inject that same instance into every future validation caller.
- Construct `AsyncFileLock` with the configured timeout, `run_in_executor=True`, `fallback_to_soft=False`, and `preserve_lock_file=True`. Unsupported native locking must fail closed rather than silently weaken serialization.

#### Acquisition, ownership, and release

`hold(track_id)` acquires in this order:

1. the cached per-track `asyncio.Lock`;
2. the cached native `AsyncFileLock`.

It releases in reverse order in a `finally` path:

1. release the native file lock;
2. leave the `asyncio.Lock` context.

The coroutine inside `async with manager.hold(track_id)` owns the lease. No caller may retain or release the underlying lock objects directly. The same task must not recursively acquire the same track lock; recursive use is a programming error and must not be relied upon.

Cancellation and exceptions have these exact outcomes:

- cancellation while waiting for the asyncio layer acquires neither layer;
- cancellation while waiting for the file layer releases the already-held asyncio layer and cannot leave a later file acquisition orphaned;
- cancellation or any exception inside the protected block releases both layers before it propagates;
- a process crash releases the native OS lock automatically;
- the stable `.lock` pathname may remain after release and is not evidence that the lock is held. Do not unlink it manually and do not implement stale-file deletion.

The protected Plan2 boundary is the entire `ValidationGate.validate(...)` transaction: suite preflight, dispatcher generation/commit, force-push, pre-trigger SHA assertion, trigger, wait, results/evidence retrieval, post-run SHA assertion, verdict, and configured `callers_pass` smoke validations. The lock is not released after push or trigger. This guarantees one validation at a time per track/SUT and one writer at a time to `agentic-eggplant-automation@Enovia`.

### `src/orchestrator/queue.py`

Replace the empty placeholder with a one-worker FIFO queue bound to a single track.

#### Public API

```python
class TrackQueue:
    def __init__(
        self,
        *,
        track_id: str,
        state_store: StateStore,
        event_bus: EventBus,
        pipeline: DiagnosisPipeline,
    ) -> None: ...

    async def start(self) -> None: ...

    async def enqueue(
        self,
        ticket: str,
        mode: RunMode,
        conversation_id: str | None,
    ) -> str: ...

    async def cancel(self, run_id: str) -> bool: ...

    async def join(self) -> None: ...

    async def shutdown(self, *, drain: bool = True) -> None: ...
```

`start()` is idempotent while the queue is open. `enqueue()` lazily calls it, so later route code cannot strand a run by forgetting startup ordering. A queue is one-shot: after `shutdown`, `start` and `enqueue` raise `RuntimeError`; construct a new queue during a new application lifespan.

#### Enqueue and queued event

For a first active request:

1. canonicalize the ticket with `strip().upper()` and reject an empty ticket with `ValueError`;
2. while holding the enqueue mutex, call:

```python
run = await AgentRun.create(
    state_store,
    event_bus,
    ticket_key=canonical_ticket,
    mode=mode,
    track_id=self.track_id,
    conversation_id=conversation_id,
)
```

3. record the same `AgentRun` in active-by-ticket and active-by-run-id maps;
4. publish the existing `run.queued` type through `EventBus.publish` with this exact payload and `cost_usd_so_far=run.cost_usd`:

```python
{
    "ticket_key": run.ticket_key,
    "track_id": run.track_id,
    "mode": run.mode,
    "conversation_id": run.conversation_id,
}
```

5. put the run onto the unbounded `asyncio.Queue` with `put_nowait` and return `run.run_id`.

Do not publish `run.queued` from `AgentRun.create`; queue admission owns that event.

If event publication fails after row creation, do not enqueue an invisible job. Persist that row as `failed` with a completion timestamp and safe `summary_json` reason `queue_admission_error`, remove it from both active maps, and re-raise. Never include raw exception text in the row.

#### Active-ticket deduplication

If the canonical ticket is already active in this track:

- do not create a row;
- do not enqueue a job;
- do not alter mode or conversation ownership;
- publish on the existing run through `EventBus.publish`:

```python
event_type = "agent.message"
payload = {"text": f"{canonical_ticket} is already running."}
cost_usd_so_far = existing_run.cost_usd
```

- return the existing `run_id`.

The enqueue mutex must remain held through the duplicate check and first-run admission so a concurrent `asyncio.gather` of identical requests yields one row, one `run.queued`, one queue item, one pipeline call, and one shared ID. Each duplicate call emits its own required `agent.message`.

An active ticket means queued or currently executing. Remove it from both active maps only after the run is terminalized, including expected failure, unexpected failure, explicit cancellation, or immediate shutdown. A later request for the same ticket then creates a new run ID.

#### Worker execution and failure isolation

- One long-lived worker calls `queue.get()` and processes items strictly one at a time.
- For a normal item, create and retain a child task for `pipeline.execute(run)` and await it. Retaining the child task allows `cancel(run_id)` to cancel one run without killing the worker.
- The call is exactly `await pipeline.execute(run)`. Do not pass a runid override and do not reconstruct the run from the database.
- Always call `queue.task_done()` exactly once and clear current-task bookkeeping in `finally`.
- Always remove a terminal run from active maps in a cancellation-safe cleanup path.
- A normal pipeline return is already terminalized by `DiagnosisPipeline`; do not publish a second terminal event.
- Catch an unexpected ordinary exception escaping `pipeline.execute`. Set the run to `failed`, set an aware UTC `completed_at`, persist status/timestamps/counters/cost and summary reason `queue_worker_error`, publish `agent.message` with exactly `{"text": "The run failed unexpectedly. Earlier artifacts were preserved."}`, then publish one `run.failed` envelope. Do not persist or publish exception text, credentials, URLs, or tracebacks. Continue to the next FIFO item.
- Never catch `BaseException`. Handle `asyncio.CancelledError` only for the explicit cancellation lifecycle below.

Use this terminal payload shape for queue-owned failure and cancellation events, matching the existing pipeline contract:

```python
{
    "summary": {
        "ticket_key": run.ticket_key,
        "status": run.status.value,
        "reason": reason,
    },
    "totals": {
        "tokens_in": run.tokens_in,
        "tokens_out": run.tokens_out,
        "cost_usd": run.cost_usd,
    },
}
```

Persist only `payload["summary"]` in `summary_json`, as `DiagnosisPipeline` does. Publish `run.failed` for a cancelled run because the binding event vocabulary has no `run.cancelled` type; its payload status remains `cancelled`, so consumers can distinguish cancellation from failure without changing the envelope contract.

#### Cancellation

`cancel(run_id)` returns `False` when the ID is unknown or already terminal and makes no change. For an active ID it returns `True` and is idempotent.

- Queued run: mark its ID cancellation-requested. Leave the item in the FIFO queue; when popped, skip the pipeline and terminalize it as `cancelled`.
- Running run: call `cancel()` on its retained pipeline child task. `DiagnosisPipeline.execute` propagates `CancelledError`; the worker catches that child cancellation, terminalizes the run as `cancelled`, and continues serving later jobs.
- Cancellation terminalization sets `RunStatus.cancelled`, an aware UTC `completed_at`, persists counters/cost and summary reason `cancelled`, publishes `agent.message` with `{"text": "Run cancelled."}`, then publishes one `run.failed` payload as defined above.
- A cancellation request must never be converted to `failed`, must never kill the worker, and must never leave the ticket in the active maps.

This method is the queue surface the later `POST /api/runs/{run_id}/cancel` route will call. Do not build the route in this step.

#### Join and shutdown

`join()` delegates to the queue's unfinished-item completion and returns only when every admitted item has either completed or been terminalized.

`shutdown(drain=True)`:

1. atomically stop accepting new work;
2. await `join()`, allowing queued and current runs to finish in FIFO order;
3. cancel only the now-idle worker blocked on `queue.get()`;
4. await worker exit and consume its `CancelledError`;
5. clear worker/current-task references.

`shutdown(drain=False)`:

1. atomically stop accepting new work;
2. request cancellation for the current run and every queued active run;
3. allow the worker to terminalize all of them as `cancelled` and satisfy every `task_done()`;
4. await `join()`, then stop the idle worker as above.

`shutdown` is idempotent. It must not leave background tasks, unfinished queue items, active-map entries, or rows stuck at `queued`. Do not rely on task garbage collection for worker or file-lock release.

### `tests/test_locks.py`

   - Two tasks using spelling/case variants of the same track never overlap their protected sections.

   - Exercise cancellation and an ordinary body exception sequentially in this one test; each propagates and a later acquisition of the same track succeeds.

6. `test_native_file_lock_excludes_another_process_then_releases`
   - Use `asyncio.create_subprocess_exec(sys.executable, "-c", ...)` with a small stdin/stdout handshake. 7. `test_process_exit_releases_native_lock`
