## Design Rulings

### Retry Safety

Use two internal request paths with one shared request-construction helper if
that avoids duplication:

```python
async def _read_request(
    self,
    method: str,
    path: str,
    **kwargs: Any,
) -> httpx.Response: ...

async def _write_request(
    self,
    method: str,
    path: str,
    *,
    operation: str,
    ticket_key: str,
    **kwargs: Any,
) -> httpx.Response: ...
```

Names may differ, but behavior must not:

- `get_ticket` and `transitions` use the retrying read path.
- A read retries on any `httpx.TimeoutException` or
  `httpx.HTTPStatusError` whose status is 500-599.
- A read makes at most three total attempts with exponential backoff. Preserve
  the existing short bounded wait (`multiplier=0.25`, `min=0.25`, `max=2`) so
  unit tests remain fast; tests may mock waiting if needed.
- Reads do not retry 4xx, connection errors other than timeout, JSON decoding
  failures, or response-shape errors.
- `post_comment`, `add_label`, `add_attachment`, and the POST inside
  `transition` use the non-retrying write path.
- A write makes exactly one HTTP request.
- A write timeout or HTTP 5xx raises `JiraWriteUncertain` from the original
  exception. A 4xx remains the original `httpx.HTTPStatusError`.

### Typed Uncertain-Write Failure

Define and export from `src/integrations/jira_client.py`:

```python
class JiraWriteUncertain(RuntimeError):
    operation: str
    ticket_key: str

    def __init__(self, operation: str, ticket_key: str) -> None: ...
```

Requirements:

- `operation` is one of `post_comment`, `add_label`, `add_attachment`, or
  `transition`.
- The message identifies the operation and ticket and says Jira may have
  completed it; callers must check Jira before retrying.
- The exception contains no body, attachment bytes, MIME data, PAT, request
  headers, authenticated URL, response body, or raw exception text.
- Chain it from the original timeout/5xx for internal debugging, but do not log
  that cause in this client.
- Do not catch it in `pipeline.py` in this step. Existing generic pipeline
  failure handling preserves truthful chat state without exposing raw errors.

### Public REST v2 Surface

Implement and preserve these exact public methods:

```python
async def get_ticket(self, key: str) -> dict[str, Any]: ...

async def post_comment(self, key: str, body: str) -> dict[str, Any]: ...

async def add_label(self, key: str, label: str) -> None: ...

async def add_attachment(
    self,
    key: str,
    filename: str,
    data: bytes,
    mime: str,
) -> list[dict[str, Any]]: ...

async def transitions(self, key: str) -> list[dict[str, Any]]: ...

async def transition(self, key: str, transition_name: str) -> None: ...
```

Behavior by method:

1. `get_ticket`
   - `GET /rest/api/2/issue/{key}`.
   - Return the complete JSON object unchanged. Do not select fields or flatten
     it: Step 1.1.2's metadata extractor searches the entire Jira response,
     including custom fields, embedded comments, and attachment names.

2. `post_comment`
   - `POST /rest/api/2/issue/{key}/comment`.
   - JSON body is exactly `{"body": body}`. Jira Data Center accepts plain text
     and wiki markup in this string.
   - Return the complete created-comment JSON object.

3. `add_label`
   - `PUT /rest/api/2/issue/{key}`.
   - JSON body is exactly
     `{"update": {"labels": [{"add": label}]}}`.
   - Accept Jira's 204 response and return `None`; never call `.json()`.

4. `add_attachment`
   - `POST /rest/api/2/issue/{key}/attachments`.
   - Add `X-Atlassian-Token: no-check` without dropping the common auth/accept
     headers.
   - Send multipart field `file` with `(filename, data, mime)` and let httpx
     construct the multipart boundary/content type.
   - Return Jira's complete attachment array. The current
     `dict[str, Any]` annotation is wrong; Data Center returns a collection even
     for one uploaded file. Validate only that the top-level payload is a list;
     raise `TypeError("Jira attachment response must be a list")` otherwise.

5. `transitions`
   - `GET /rest/api/2/issue/{key}/transitions`.
   - Return `payload["transitions"]`.
   - Preserve the current shape guard: a missing/non-list `transitions` value
     raises `TypeError("Jira transitions response must contain transitions[]")`.

6. `transition`
   - Call `transitions(key)` and match `name` case-insensitively using
     `casefold()`.
   - If absent, emit the existing structured warning
     `jira_transition_not_found` with `key` and requested `transition`, make no
     POST, and return `None`.
   - If present, require its `id`, convert it to `str`, and
     `POST /rest/api/2/issue/{key}/transitions` with body
     `{"transition": {"id": "<id>"}}`.
   - Accept Jira's 204 response and return `None`.
  - Do not swallow 4xx or uncertain-write failures. "Best-effort" means an
     unavailable named transition is a no-op and later lifecycle callers may
     isolate transition failure; it does not mean the HTTP client falsifies
     success.

## Deferred User-Visible Retry Contract

The User requires a reopened chat session to show which operation failed and to
offer a check/retry path. The current persistence/event architecture already
supports the first half: failed step and run events survive and replay.

The second half belongs to the later chat/lifecycle owner and must follow these
rules when briefed:

- Display the persisted failed Jira operation and whether its outcome is
  uncertain.
- Do not retry merely because the browser reopened or SSE reconnected.
- For `JiraWriteUncertain`, first check Jira for the intended effect using an
  operation-specific reconciliation read.
- If present, mark the operation reconciled without repeating it.
- If absent, offer an explicit user retry that creates an auditable event.
- If the check cannot decide, preserve the uncertain state and require manual
  confirmation; never claim success or repeat blindly.

Do not implement this deferred contract in Step 1.2.1.
