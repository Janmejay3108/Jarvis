Decision 003, **Retry Jira Reads, Surface Uncertain Writes**, fixes the transport boundary:

> Every write is attempted exactly once. A timeout or retryable server outcome is surfaced as

> Jira publication is not part of diagnosis truth. A diagnosis run remains completed when a Jira

> retain `JiraWriteUncertain -> uncertain`; retain definite HTTP 4xx -> `failed` and ambiguous HTTP
> 5xx -> `uncertain`; identify the actual transport exceptions that can make write outcome
> unknowable; do not classify arbitrary programming defects (`TypeError`, `AttributeError`,
> assertion failures) as `uncertain` human-reconciliation work; define the durable action state
> left when such a programming defect propagates; preserve independent comment/label attempts where
> the failure is a publication outcome, without swallowing a pipeline bug.

### Local Finding And Required Resolution

`DiagnosisPipeline._attempt_jira_write` currently ends with:

```python
except Exception:  # noqa: BLE001
    state = "uncertain"
```

That blanket catch converts software defects raised by a Jira adapter or test double into ordinary
human-reconciliation work. It also lets the diagnosis run complete even though the pipeline itself
is defective.

Use `httpx.RequestError` as the narrow transport boundary. It is the httpx base class for request
transport failures such as connect, read, write, protocol, pool, and timeout failures. At the
pipeline boundary the write outcome cannot be proven from those exceptions, so the durable Jira
action state is `uncertain`. `httpx.HTTPStatusError` remains separate because an HTTP response was
received and its status determines `failed` versus `uncertain`.

Do not catch `TypeError`, `AttributeError`, `AssertionError`, `RuntimeError`, `ValueError`, or a new
project-wide exception superclass. Such defects must leave `_attempt_jira_write` and reach the
pipeline's existing `execute()` terminal boundary. `execute()` must continue converting them into a
safe failed run with reason `pipeline_error`; this step does not change the public execute contract
to re-raise ordinary exceptions to the caller.

The durable action state after such a defect is intentionally:

- `state == "pending"`;
- `attempts == 1`;
- the persisted/replayed action-event sequence for that action records creation (`pending`, attempt
  0) and attempt start (`pending`, attempt 1), with no fabricated `failed` or `uncertain` outcome.

This is the honest crash-window state. A programming exception may occur before transmission, during
an adapter call, or while interpreting a response after Jira accepted the write. Classifying it as
`failed` could authorize a duplicate; classifying it as `uncertain` would hide the software defect
as human reconciliation. The failed run makes the defect visible while the pending action preserves
what JARVIS can actually prove.
