# Plan1 Step 1.1.2 Follow-up: Jira Action Reconciliation

## Authority And Scope

This follow-up implements Decision 004 on top of the Jira transport boundary built for Decision
003. It is the diagnosis-side portion of Plan1 Step 1.1.2, not Step 1.5.3 or Step 1.6.2.

Plan1 Step 1.1.2 is binding:

> **Jira publication is a side effect, not the diagnosis.** A successful diagnosis stays a
> **successful run** even when publication fails or is uncertain — a Jira outage must never be
> reported as a failed diagnosis.

> **Each write is attempted independently.** A failed comment must NOT prevent the
> `ai-diagnosed` label attempt, and vice versa.

> **Schema addition** (a migration on plan0 §B.6's store, *not* a new store):
> `jira_actions(action_id, run_id, ticket_key, operation, intent_json, state, check_result,
> attempts, created_at, updated_at)`.

Decision 003 remains binding:

> Reads retry 3× with exponential backoff. Writes make exactly one attempt and are never
> auto-retried.

The current defect is local and proven: `DiagnosisPipeline._post_diagnosis` performs comment then
label in one `_stage`; any exception reaches `_stage`, which calls `AgentRun.end(error=...)`, emits
`step.failed`, and terminalizes the run. The Builder must absorb Jira publication degradation
inside `_post_diagnosis`, after durably recording it, so the enclosing stage completes normally.

### `src/orchestrator/jira_actions.py` — new shared action contract

Create the reusable vocabulary that later Plan1 routes and Plan3 lifecycle writes must import.
Do not let those phases invent their own state strings or event serializer.

```python
from collections.abc import Mapping
from typing import Any, Literal

JiraActionState = Literal[
    "pending", "succeeded", "failed", "uncertain", "reconciled"
]
JiraCheckResult = Literal["present", "absent", "unknown"]

JIRA_ACTION_STATES: frozenset[str]
JIRA_CHECK_RESULTS: frozenset[str]

def jira_action_event_payload(action: Mapping[str, Any]) -> dict[str, Any]: ...
def append_jira_action_footer(body: str, action_id: str) -> str: ...
```

`jira_action_event_payload` returns **exactly** these keys:

```text
action_id, operation, state, check_result, attempts, created_at, updated_at
```

It must not copy `run_id`, `ticket_key`, `intent`, `intent_json`, request body, exception text,
response text, URLs, credentials, or any unknown key. The event envelope already carries `run_id`.

`append_jira_action_footer` appends this exact plain-text marker, preserving the formatter body:

```text
\n\n[JARVIS action_id=<action_id>]
```

The marker is intentionally inspectable in Jira's comment-list response for Step 1.5.3
reconciliation. It is not hidden markup.

### `src/orchestrator/state_store.py` — additive migration and CRUD

Extend `_SCHEMA`; do not create a second database or migration framework. `initialize()` must
remain idempotent on both a new database and an existing six-table plan0 database.

```sql
CREATE TABLE IF NOT EXISTS jira_actions (
    action_id TEXT PRIMARY KEY,
    run_id TEXT NOT NULL,
    ticket_key TEXT NOT NULL,
    operation TEXT NOT NULL,
    intent_json TEXT NOT NULL,
    state TEXT NOT NULL CHECK (
        state IN ('pending', 'succeeded', 'failed', 'uncertain', 'reconciled')
    ),
    check_result TEXT NOT NULL CHECK (
        check_result IN ('present', 'absent', 'unknown')
    ),
    attempts INTEGER NOT NULL CHECK (attempts >= 0),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS jira_actions_run_id_idx
ON jira_actions(run_id);
```

Do not retrofit foreign keys onto the existing plan0 schema in this slice.

Add these methods, following the existing dictionary/JSON hydration style:

```python
async def create_jira_action(
    self,
    run_id: str,
    ticket_key: str,
    operation: str,
    intent: Mapping[str, Any],
    *,
    action_id: str | None = None,
) -> dict[str, Any]: ...

async def get_jira_action(self, action_id: str) -> dict[str, Any] | None: ...

async def list_jira_actions(self, run_id: str) -> list[dict[str, Any]]: ...

async def begin_jira_action_attempt(self, action_id: str) -> dict[str, Any]: ...

async def update_jira_action(
    self,
    action_id: str,
    *,
    state: JiraActionState,
    check_result: JiraCheckResult | None = None,
    attempts: int | None = None,
) -> dict[str, Any]: ...
```

Required behavior:

- `create_jira_action` commits before returning. It stores `state="pending"`,
  `check_result="unknown"`, `attempts=0`, and identical UTC ISO-8601 `created_at` / `updated_at`.
- Generate `action_id` with the store's existing ID helper unless supplied by a test.
- Store `intent` as JSON in `intent_json`; hydrated rows expose it as `intent` and do not expose
  `intent_json`.
- `list_jira_actions` is deterministic insertion order for one run.
- `begin_jira_action_attempt` atomically increments `attempts`, keeps/sets `state="pending"`, updates
   `updated_at`, commits, returns the hydrated row, and raises `KeyError(action_id)` when absent. Call
   it immediately before each network write and publish the returned pending state before issuing
   that write. A crash after this commit is conservatively an initiated attempt requiring a later
   check, never a blind retry.
- `update_jira_action` validates state/check-result/attempt count, updates `updated_at`, commits,
  returns the hydrated row, and raises `KeyError(action_id)` if no row exists. No generic
  caller-supplied SQL field map.
- `intent` for this slice is safe reconstruction metadata only:
  - comment: `{"kind": "diagnosis_comment", "source": "diagnosis_artifact"}`;
  - label: `{"label": "ai-diagnosed"}`.
- Never store the formatted comment body, PAT, authenticated URL, attachment bytes, MIME, exception
  text, raw request/response text, or Jira response payload.

### `src/orchestrator/pipeline.py` — independent durable side effects

Keep `DiagnosisPipeline.__init__` and `JiraGateway` signatures stable. Add private helpers only;
do not move reconciliation policy into `JiraClient`.

For each diagnosis-side operation:

1. Call `create_jira_action` and publish `jira.action.updated` with the allowlisted payload **before
   any formatter or network call** (`pending`, attempts 0).
2. After operation-specific preparation succeeds, call `begin_jira_action_attempt` and publish its
   returned state (`pending`, attempts 1) immediately before the network request.
3. Issue at most one Jira write.
4. Persist the terminal action state and publish another `jira.action.updated`.
5. Swallow the publication outcome into a safe aggregate completion detail; do not pass an error
   to `AgentRun.end` and do not emit `step.failed` or `run.failed` for it.
6. Continue to the other operation regardless of the first operation's result.

Use this outcome classification:

- success → `succeeded`;
- `JiraWriteUncertain` → `uncertain`;
- `httpx.HTTPStatusError` with a 4xx response → `failed`;
- any other ordinary `Exception` from a Jira write → conservatively `uncertain`, because the caller
  cannot prove whether the side effect occurred;
- formatter failure occurs before `begin_jira_action_attempt` and is therefore `failed` with
   `attempts=0` and zero Jira requests;
- do **not** catch `asyncio.CancelledError` / other `BaseException`: it propagates and leaves the
  already-committed action `pending`, with its pending event durable. This is the crash window.

For the comment, create the action first, format the diagnosis, then append the exact action footer
before the single `post_comment` call. For the label, create its own action and call `add_label`
once. Publish every action event with `cost_usd_so_far=run.cost_usd`.

The completed `post_diagnosis` step detail must be deterministic and safe:

- both succeeded: `Jira publication succeeded (2/2 actions)`;
- otherwise: `Diagnosis completed; Jira publication needs attention: ` followed by
  `post_comment=<state>, add_label=<state>` in that order.

When `jira_writes_enabled` is false, preserve current behavior exactly: no formatter call, no Jira
action rows/events, no Jira requests, detail `Jira writes disabled`.

The existing terminal persistence after `_post_diagnosis` remains responsible for completing the
successful run. Do not add a second run-completion path.
